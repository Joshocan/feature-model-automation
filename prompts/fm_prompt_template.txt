METAMODEL SPECIFICATION:

The model must satisfy these conditions.

  W1  Exactly one feature has no parent, and it is named {{ROOT_FEATURE}}.
  W2  Every feature name is unique within the model.
  W3  A requires or excludes constraint has exactly two operands.
  W4  Every feature named in a constraint exists in the model.
  W5  A constraint carries a formula only when it is not a plain requires or excludes.

Structural rules:
  - Every non-root feature has exactly one parent.
  - The parent relation is acyclic.
  - Members of an <or> or <alt> group are children of the same parent.

Permitted attributes on feature and group nodes: name, abstract, mandatory.

{# ---------------- BLOCK C: output contract (ALWAYS, including ablation) ---------------- #}
OUTPUT CONTRACT:

Output a single FeatureIDE XML feature model and nothing else.
No markdown, no code fences, no commentary, no explanation.
No text before <?xml ...?> and no text after </featureModel>.
Stop immediately after </featureModel>.

Skeleton:
  <?xml version="1.0" encoding="UTF-8"?>
  <featureModel>
    <struct> ... </struct>
    <constraints> ... </constraints>
  </featureModel>

Emit <constraints/> when there are none.

Feature names must be valid identifiers, because they are parsed as propositional
variables. A name starts with a letter or an underscore and continues with letters,
digits or underscores only. No spaces, hyphens, dots, slashes or any other punctuation.
Replace every separator with an underscore: write delta_based, not delta-based;
Element_value, not Element.value.

Each <rule> contains exactly one formula tree:
  requires(A,B)  <rule><imp><var>A</var><var>B</var></imp></rule>
  excludes(A,B)  <rule><disj><not><var>A</var></not><not><var>B</var></not></disj></rule>
Never place text directly in <rule>, and never place two formula roots in one <rule>.

{# ---------------- BLOCK D: modelling guidance (ALWAYS) ---------------- #}
MODELLING GUIDANCE:

Fidelity
  - Use only features and constraints the evidence supports. Do not invent.
  - Use the terminology of the source text for feature names where possible.
  - When the text enumerates alternatives, kinds, formalisms, operations or artefact
    types, model each as its own sibling feature rather than merging them into one.

Structure
  - Reflect the organisation the text presents. Introduce an intermediate grouping
    where the text groups concepts, and not otherwise.
  - Mark a feature abstract="true" when it exists only to group its children.

Variability
  - Mark mandatory="true" when the evidence indicates the feature holds whenever its
    parent does. Omit mandatory when the evidence presents it as one possibility among
    others. Where the evidence does not settle it, choose the reading the text better
    supports rather than defaulting in either direction.
  - <and> for co-existing decomposition, <or> for one-or-more, <alt> for exactly-one.
    Use <alt> only where the alternatives are mutually exclusive in the evidence.
  - Do not mix group kinds within one group.

Naming
  - Deduplicate synonyms; keep one expressive name per concept.
  - Distinct concepts must not share a name, even under different parents.

{# ---------------- BLOCK E: provenance (ALWAYS) ---------------- #}
PROVENANCE:

Every feature carries exactly one <description> element of at least one full sentence,
grounded in the evidence.

Every description, without exception, ends with a trace in exactly this form, as the
final characters of the description:

  Trace: [id1, id2]

Rules for the trace:
  - Use ONLY document identifiers listed under DOCUMENT IDS IN THIS CONTEXT below.
  - Identifiers exactly as given. Do not abbreviate, reformat or invent them.
  - Separate multiple identifiers with a comma and a space.
  - At least one identifier. No section numbers, headings, titles or page numbers.
  - Nothing after the closing bracket.

Abstract features carry a trace as well. An abstract feature exists to group its
children, so its trace lists the identifiers supporting the features grouped beneath
it. Do not cite a document for an abstract feature unless that document supports at
least one feature below it.

Form of a description:
  <description>One sentence stating what the feature is, in the terms the evidence
  uses. Trace: [ID_A, ID_B]</description>

{% if previous_model %}
Traces already present in the PREVIOUS FEATURE MODEL are kept unchanged, even when
they name documents absent from this context. Add an identifier to an existing trace
only when this context provides further evidence for that same feature.
{% endif %}

{# ---------------- BLOCK F: refinement policy [[SWITCH: previous_model]] ---------------- #}
{% if previous_model %}
REFINEMENT POLICY:

Preserve, then refine.
  - Carry every feature of the PREVIOUS FEATURE MODEL into the output by default.
  - Remove a feature only where this context contradicts it. Prefer re-parenting to
    deletion.
  - Add from this context only what the previous model lacks. Do not restate a concept
    already present under a near-duplicate name.
  - Extend the hierarchy before restructuring it. Re-parent an existing feature or
    introduce a new grouping only where this context gives a reason to.
  - Never merge distinct concrete features into one. Two named techniques remain two
    features even when grouped under a new parent.
  - Keep existing descriptions. Update one only where re-parenting has made it
    inaccurate.

Output the complete updated model, not a diff and not a summary.
